Исследование целевой модели результата BuildThemeComponentsStage

Нулевая версия (v0.0)

Статус:
Working Draft / Research

Контекст

```
Документ фиксирует первую рабочую модель результата BuildThemeComponentsStage,
полученную исключительно из материалов уже завершённой части исследования.

Документ не является архитектурной спецификацией.

Все положения могут быть изменены или полностью пересмотрены
по результатам дальнейшего исследования.
```

================================================================================

1. ЦЕЛЬ
   ================================================================================

   Определить, какой должна быть идеальная модель, формируемая
   BuildThemeComponentsStage.

   Данная модель должна стать фундаментом всей последующей
   компиляции темы независимо от реализации Theme IR
   и генераторов артефактов.

================================================================================
2. ПОДТВЕРЖДЁННЫЕ НАБЛЮДЕНИЯ
============================

```
На текущем этапе исследования можно считать подтверждёнными
следующие положения.

1. Каждый компонент, формируемый BuildThemeComponentsStage,
    должен быть декларативной моделью своей области ответственности,
    полностью отделённой от исполнения, генерации артефактов и особенностей целевой платформы.

2. Модель должна описывать предметную область,
    а не механизм её исполнения.

3. Модель должна быть независима
    от WordPress Runtime.

4. Модель должна быть независима
    от конечных артефактов.

5. Модель должна являться единственным источником данных
    для последующих стадий Pipeline.

6. Новые разновидности тем не должны требовать изменения
    фундаментальной структуры модели.

7. Каждая концепция должна иметь единственное место
    внутри модели.

8. Архитектура модели должна определяться
    найденными инвариантами предметной области,
    а не существующей реализацией.
```

================================================================================
3. ТЕКУЩИЕ ТРЕБОВАНИЯ К МОДЕЛИ
==============================

```
Идеальная модель должна:

    • описывать тему полностью;

    • быть детерминированной;

    • быть расширяемой;

    • быть независимой от способов исполнения;

    • быть независимой от способов генерации;

    • быть пригодной для преобразования
        в Theme IR;

    • быть пригодной для генерации
        любых поддерживаемых артефактов.
```

================================================================================
4. НЕПОДТВЕРЖДЁННЫЕ ВОПРОСЫ
===========================

```
На текущем этапе отсутствуют основания считать установленными:

    • набор фундаментальных доменов;

    • фундаментальную форму модели
        (дерево, граф, сеть и т.п.);

    • минимальную архитектурную единицу модели;

    • полный перечень фундаментальных концепций;

    • отношения между фундаментальными концепциями.
```

================================================================================
5. РАБОЧАЯ ГИПОТЕЗА
===================

```
Предполагается, что существующие домены
(Assets, Templates, Compositions, Design System,
Integrations и другие)

могут являться не фундаментальными сущностями,
а лишь различными проявлениями
более глубоких архитектурных инвариантов.

Данная гипотеза требует дальнейшего исследования.
```

================================================================================
6. ЦЕЛЬ ДАЛЬНЕЙШЕГО ИССЛЕДОВАНИЯ
================================

```
Последующие документы должны позволить определить:

    • минимальный набор фундаментальных концепций;

    • их взаимные отношения;

    • структуру идеальной модели результата
        BuildThemeComponentsStage;

    • критерии её полноты и устойчивости.
```

================================================================================
ТЕКУЩИЙ ВЕРДИКТ
===============

```
На данном этапе исследование не направлено
на проектирование конкретных компонентов.

Главная задача —
обнаружить фундаментальные архитектурные инварианты,
на основе которых позднее будет построена окончательная
модель результата BuildThemeComponentsStage.
```


ПРИНЦИПЫ ВЫДЕЛЕНИЯ КОМПОНЕНТОВ

    Компонент должен представлять самостоятельную
    фундаментальную концепцию предметной области.

    Если вся информация о некоторой концепции
    полностью выводится из других компонентов,
    отдельный компонент не создаётся.

    Производные концепции должны вычисляться
    на последующих стадиях Pipeline.

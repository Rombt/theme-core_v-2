Исследование целевой модели результата BuildThemeComponentsStage

Версия 1.0.0

Статус:
Working Draft / Research Specification

================================================================================
1. ЦЕЛЬ ИССЛЕДОВАНИЯ
================================================================================

    Выявление минимальной архитектурной модели,
        достаточной для качественной реализации системы.

    Определить метамодель компонентов, формируемых BuildThemeComponentsStage.

    Для этого необходимо выявить фундаментальные архитектурные инварианты,
        которым должен удовлетворять каждый компонент.

    Результатом исследования должна стать модель, достаточная для проектирования
        и реализации системы ThemeComponents.

================================================================================
2. ОБЪЕКТ ИССЛЕДОВАНИЯ
================================================================================

    Объект исследования:
        результат выполнения BuildThemeComponentsStage.

    На текущем этапе результат рассматривается не как набор конкретных доменов:

        Assets
        Compositions
        Templates
        Design System
        Integrations

    а как коллекция компонентов, каждый из которых должен соответствовать
        единой фундаментальной модели.


================================================================================
3. ОСНОВНАЯ ГИПОТЕЗА
================================================================================

    ThemeComponent является универсальной архитектурной единицей ThemeCore.

    Различные доменные компоненты являются специализациями
        общей метамодели ThemeComponent.

================================================================================
4. ФУНДАМЕНТАЛЬНЫЕ ТРЕБОВАНИЯ К КОМПОНЕНТУ
================================================================================

    Каждый компонент BuildThemeComponentsStage должен:

        4.1 Представлять самостоятельную область знаний.
        -------------------------------------------------------------------------------

            Компонент должен содержать информацию, которая не может быть
            полностью выведена из других компонентов.


        4.2 Быть декларативной моделью.
        -------------------------------------------------------------------------------

            Компонент описывает существующие знания предметной области.

            Компонент не описывает:
                - алгоритмы выполнения;
                - порядок исполнения;
                - генерацию результата;
                - детали реализации.


        4.3 Быть независимым от физического представления.
        -------------------------------------------------------------------------------

            Компонент описывает логические сущности.

            Файлы, форматы хранения, WordPress API, HTML, CSS, PHP и другие формы реализации
                относятся к последующим стадиям Pipeline.


        4.4 Иметь собственную ответственность.
        -------------------------------------------------------------------------------

            Каждый компонент должен отвечать за одну фундаментальную область знаний.

            Пересечение ответственности между компонентами должно отсутствовать.


        4.5 Быть преобразуемым в последующую модель.
        -------------------------------------------------------------------------------

            Каждый компонент должен иметь возможность детерминированного преобразования
                в следующую внутреннюю модель Pipeline.


================================================================================
5. КРИТЕРИИ ФУНДАМЕНТАЛЬНОСТИ КОМПОНЕНТА
================================================================================

    Концепция может быть представлена отдельным компонентом только если:

        1. Она содержит собственные знания.

        2. Она не является полностью производной
        от других компонентов.

        3. Она имеет самостоятельную область ответственности.

        4. Её отсутствие приводит к потере информации
        о теме.

================================================================================
6. КРИТЕРИИ ПРОИЗВОДНОЙ КОНЦЕПЦИИ
================================================================================

    Концепция не должна становиться отдельным компонентом если:

        - её данные полностью содержатся в другом компоненте;
        - она может быть детерминированно получена на последующих стадиях Pipeline;

        - она описывает только способ представления другой концепции.


================================================================================
7. ПРЕДВАРИТЕЛЬНАЯ МЕТАМОДЕЛЬ КОМПОНЕНТА
================================================================================

    ThemeComponent

        ├── Identity
        │
        ├── Domain Knowledge
        │
        ├── Relationships
        │
        ├── Constraints
        │
        └── Metadata


    Данная структура является рабочей гипотезой и требует проверки последующими исследованиями.

================================================================================
8. ПРИМЕНЕНИЕ К СУЩЕСТВУЮЩИМ КОНЦЕПЦИЯМ
================================================================================

    Предварительно:

        Composition
            Подтверждённые свойства:
                - декларативная структура;
                - собственная область знаний;
                - независимость от генерации.


        Asset
            Подтверждённые свойства:
                - описание логического ресурса;
                - независимость от файловой реализации;
                - собственная область знаний.


        Template
            Предварительный вывод:
                - производная концепция;
                - отдельный компонент не требуется.

================================================================================
9. ОТКРЫТЫЕ ВОПРОСЫ
================================================================================

    Требуют дальнейшего исследования:

        1. Какие именно элементы входят в Domain Knowledge?
        2. Являются ли Relationships частью компонента или отдельным фундаментальным типом?
        3. Достаточна ли предложенная метамодель для всех типов компонентов?
        4. Какие существующие домены ThemeCore являются фундаментальными компонентами?
        5. Как выглядит итоговая структура ThemeComponent на уровне PHP-модели?

================================================================================
10. ТЕКУЩИЙ ВЕРДИКТ
================================================================================

    Исследование переходит от поиска списка доменов
    к определению фундаментальной модели компонента.

    Главная задача дальнейшего исследования:

        определить минимальную метамодель ThemeComponent,
        достаточную для описания всех фундаментальных
        компонентов BuildThemeComponentsStage.

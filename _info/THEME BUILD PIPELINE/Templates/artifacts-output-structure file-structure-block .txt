ARTIFACT OUTPUT TYPES AND FILE STRUCTURE
ARCHITECTURAL DESCRIPTION
(v1.0.0)

Status: Architectural Foundation

==================================================
1. PURPOSE
==================================================

   Данный документ фиксирует архитектурное решение
    по классификации элементов Theme Configuration
    для определения структуры результирующих файлов
    генерируемой WordPress Block Theme.

   Решение предназначено для
    Block Theme Architecture.

   Основная цель:

   отделить семантическую классификацию элементов
    от физического пути результирующего файла

   обеспечить автоматическое определение
    способа и места материализации Artifact

   сохранить конфигурацию независимой
    от конкретной файловой структуры темы

   использовать нативную файловую модель WordPress Block Theme

   обеспечить масштабирование конфигурационного
    пакета без необходимости вручную указывать
    пути сохранения каждого элемента.

==================================================
2. CORE PRINCIPLE
==================================================

    Поле type конфигурационного элемента
    используется как семантический классификатор.

    type определяет роль элемента  в результирующей теме.

    type НЕ определяет физический путь файла.

    Физическое расположение и способ материализации
        Artifact определяются Artifacts Layer
        на основании семантики элемента,
        rendering и текущей архитектуры.

    Таким образом:

        Theme Configuration
            ↓
        semantic type
            ↓
        ThemeIR
            ↓
        Block Architecture Artifacts
            ↓
        rendering
            ↓
        output file structure


    Конфигурация не должна содержать физические пути результирующих файлов.

==================================================
3. TYPE
==================================================

    type — закрытая семантическая классификация Node
        или Composition по его основной предметной
        и структурной роли.

    Выбор производится по наиболее специфичной семантике.

    Для классификации элементов принимается
        минимальный набор из восьми типов:

            template
            layout
            post
            page
            product
            navigation
            form
            common

    Набор типов является закрытым.

    Набор типов является минимальным и не должен расширяться без необходимости.

    Новый тип вводится только в случае,
        если существующие типы не позволяют
        однозначно классифицировать новый элемент
        и определить его семантическую роль.

==================================================
4. TYPE: TEMPLATE
==================================================

    template обозначает основной шаблон  WordPress Block Theme.

    Такие элементы материализуются в директории:

        templates/

    Формат Artifact:
        templates/<template-name>.html

    Примеры:

        templates/index.html
        templates/single.html
        templates/page.html
        templates/archive.html
        templates/category.html
        templates/tag.html
        templates/search.html
        templates/404.html

    template является специальным типом в отношении файловой структуры Block Theme.

    Artifact типа template является самостоятельным top-level Template.

==================================================
5. TYPE: LAYOUT
==================================================

    layout обозначает крупную структурную часть страницы или шаблона.

    type layout сам по себе не определяет способ материализации.

    При rendering:
        template-part

    элемент материализуется как Template Part непосредственно в:
        parts/

    Примеры:

        header
        footer
        sidebar
        layout
        hero
        section
        grid

    Возможный Artifact:

        parts/header.html
        parts/footer.html
        parts/sidebar.html
        parts/layout-01.html

    Layout может также иметь rendering:
        inline

    В этом случае отдельный Artifact не создаётся, а содержимое элемента
        встраивается в родительский Artifact.

==================================================
6. TYPE: POST
==================================================

    post обозначает элементы, предназначенные для представления записи
        или работы с её содержимым.

    type post не определяет физическую директорию.

    При rendering:

        template-part

    элемент материализуется непосредственно в:

        parts/

    Примеры:

        post-loop
        post-card
        post-meta
        query

    Возможные Artifacts:

        parts/post-loop.html
        parts/post-card.html
        parts/post-meta.html

    При rendering:

        inline

    элемент не создаёт отдельный Artifact.

    Его Block markup встраивается непосредственно в родительский Artifact.

    Например:

        post_title_01
            ↓
        <!-- wp:post-title /-->

===================================================
7. TYPE: PAGE
===================================================

    page обозначает элементы, специфичные для представления страницы.

    type page не определяет физическую директорию.

    При rendering:

        template-part

    элемент материализуется непосредственно
    в:

        parts/

    Примеры:

        page-content
        page-section

    Возможный Artifact:

        parts/page-content.html

    При rendering:

        inline

    элемент встраивается непосредственно в родительский Artifact.

==================================================
8. TYPE: PRODUCT
==================================================

    product обозначает элементы, относящиеся к представлению товара
        и функциональности e-commerce.

    type product не определяет физическую директорию.

    При rendering:

        template-part

    Artifact материализуется непосредственно
    в:

        parts/

    Примеры:

        product-card
        product-price
        product-gallery

    Возможные Artifacts:

        parts/product-card.html
        parts/product-price.html
        parts/product-gallery.html

    При rendering:

        inline

    отдельный Artifact не создаётся.

==================================================
9. TYPE: NAVIGATION
==================================================

    navigation обозначает элементы, предназначенные для навигации сайта.

    type navigation не определяет физическую директорию.

    При rendering:

        inline

    Block markup навигации встраивается непосредственно
        в родительский Artifact.

    Например:

        navigation_01
            ↓
        <!-- wp:navigation ... /-->

    При rendering:

        template-part

    элемент может быть материализован как самостоятельный Template Part:

        parts/<artifact-name>.html

    Выбор rendering определяется конфигурацией и семантикой элемента.

==================================================
10. TYPE: FORM
==================================================

    form обозначает элементы, относящиеся к формам и их составным элементам.

    type form не определяет физическую директорию.

    При rendering:

        template-part

    Artifact материализуется непосредственно в:

        parts/

    При rendering:

        inline

    элемент встраивается непосредственно в родительский Artifact.

    Отдельные типы:

        input
        textarea
        select
        checkbox
        radio
        button

    не создаются.

==================================================
11. TYPE: COMMON
==================================================

    common обозначает универсальные элементы, которые не относятся однозначно
        к специализированному домену.

    type common не определяет физическую директорию.

    При rendering:

        template-part

    Artifact материализуется непосредственно в:

        parts/

    При rendering:

        inline

    элемент встраивается непосредственно в родительский Artifact.

    Примеры:

        no-posts
        pagination
        separator
        site-title
        copyright

    Для атомарных Gutenberg Blocks предпочтительным способом материализации является:

        inline

    Например:

        site_title_01
            ↓
        <!-- wp:site-title ... /-->

        no_posts_01
            ↓
        <!-- wp:paragraph ... /-->

==================================================
12. BLOCK THEME SPECIAL FILES
==================================================

    Block Theme имеет специальные категории файлов, которые не определяются
        значением type Node или Composition.

    К ним относятся:

        style.css
        functions.php
        theme.json

    Также Block Theme может содержать:

        patterns/
        styles/
        assets/
        inc/

    Эти категории имеют собственные правила Artifacts Layer.

    Они не должны добавляться в набор semantic type.

    В частности, создание типов:

        pattern
        style
        asset
        configuration

    для описания существующих Theme Configuration Node не требуется.

==================================================
13. TEMPLATE PARTS
==================================================

    Template Parts являются самостоятельными повторно используемыми частями Block Theme.

    Они материализуются непосредственно в директории:

        parts/

    В Block Theme не используется классификация Template Parts
        по вложенным директориям.

        Недопустимая структура:

            parts/post/
            parts/page/
            parts/navigation/
            parts/common/

    Допустимая структура:

        parts/
            header.html
            footer.html
            sidebar.html
            post-loop.html
            post-card.html

    Семантический type элемента не должен приводить к созданию
        отдельной директории внутри parts/.

==================================================
14. NODE AND TYPE
==================================================

    Node содержит type,
    который описывает семантическую роль Node.

    type не должен содержать:

        имя директории
        имя файла
        расширение файла
        абсолютный путь
        относительный путь

    Node остаётся частью декларативной модели Theme Configuration.

    Node может материализоваться:

        inline

    или:

        template-part

    в зависимости от его rendering и семантики.

    Не каждый Node обязан создавать Artifact.

==================================================
15. COMPOSITION AND TYPE
==================================================

    Каждая Composition должна иметь поле type.

    type Composition определяется в соответствии с её семантической ролью
        в результирующей теме.

    Composition использует тот же утверждённый набор типов, что и Node.

    Различие между Node и Composition определяется их структурной ролью:

        Node
            атомарный элемент

        Composition
            составной элемент

    Composition может материализоваться как самостоятельный Template Part,
        если её rendering определяет:

        template-part

    В этом случае Artifact создаётся непосредственно в:

        parts/

    Composition с rendering:

        inline

    не создаёт отдельный Artifact и встраивается в родительский Artifact.

==================================================
16. RELATION TO RENDERING
==================================================

    type и rendering имеют разные значения.

    type отвечает на вопрос:

        "К какой семантической категории относится элемент?"

    rendering отвечает на вопрос:

        "Как элемент должен быть материализован в Block Architecture?"

    Основные значения:
        inline
        template-part
        template

    rendering не является заменой type.

    Пример:

        type:
            post

        rendering:
            inline

    означает:

        семантическая категория:
            post

        способ материализации:
            inline Block markup

    Другой пример:

        type:
            layout

        rendering:
            template-part

    означает:

        семантическая категория:
            layout

        способ материализации:
            самостоятельный Template Part

==================================================
17. MATERIALIZATION RULES
==================================================

    Для Block Architecture применяются
    следующие основные правила.

    1. ype = template
            ↓
        templates/<artifact-name>.html


    2. rendering = template-part
            ↓
        parts/<artifact-name>.html

    3. rendering = inline
            ↓
        отдельный Artifact не создаётся
            ↓
        Block markup встраивается в родительский Artifact

    type не определяет, будет ли элемент inline или Template Part.

    Это определяется rendering и семантикой конкретного элемента.

==================================================
18. CURRENT BLOCK OUTPUT STRUCTURE
==================================================

    Базовая структура Block Theme:

        theme/
        │
        ├── style.css
        ├── functions.php
        ├── theme.json
        │
        ├── templates/
        │   ├── index.html
        │   ├── single.html
        │   ├── page.html
        │   ├── archive.html
        │   ├── category.html
        │   ├── tag.html
        │   ├── search.html
        │   └── 404.html
        │
        ├── parts/
        │   ├── header.html
        │   ├── footer.html
        │   ├── sidebar.html
        │   ├── post-loop.html
        │   └── ...
        │
        ├── patterns/
        │   └── ...
        │
        ├── styles/
        │   └── ...
        │
        ├── assets/
        │   └── ...
        │
        └── inc/
            └── ...

    Конкретные файлы определяются Artifacts Layer.

    Наличие дополнительных директорий определяется функциональностью темы.

==================================================
19. TEMPLATE PART INTEGRATION
==================================================

    При материализации Composition как Template Part:

        parts/<artifact-name>.html

    подключение Template Part из другого Block Artifact выполняется средствами
        WordPress Block Markup.

        Например:

            <!-- wp:template-part {"slug":"header"} /-->

    Artifact Layer отвечает за формирование корректной ссылки на Template Part.

        Физический путь:

            parts/header.html

        и значение slug:

            header

        должны соответствовать друг другу.

==================================================
20. ARTIFACT FILENAME
==================================================

    Имя Artifact определяется Artifacts Layer на основании
        семантики элемента и правил Block Architecture.

    Для стандартных WordPress Templates используются стандартные имена:

        index.html
        single.html
        page.html
        archive.html
        category.html
        tag.html
        search.html
        404.html

    Для Template Parts используются имена, соответствующие назначению
        элемента:

        header.html
        footer.html
        sidebar.html
        post-loop.html
        post-card.html

    Для пользовательских файлов темы применяются правила:

        только lowercase
        слова разделяются дефисами
        camelCase не используется
        underscore не используется

    Например:

        post_title_01
            ↓
        post-title-01.html

        post_loop_01
            ↓
        post-loop-01.html

    Внутренний идентификатор конфигурации не обязан напрямую определять имя Artifact.

    Artifacts Layer может преобразовать внутренний идентификатор в подходящее
        имя результирующего файла.

==================================================
21. CURRENT CONFIGURATION MAPPING
==================================================

    На текущем конфигурационном пакете:

        index
        single
        page
        category
        tag
            → template


        header
        footer
        sidebar
        layout
        post-loop
        query
            → layout/post
            + rendering=template-part
            → parts/


        navigation_01
        footer_navigation_01
        hero_navigation_01
        site_title_01
        archive_title_01
        copyright_01
            → rendering=inline
            → inline Block markup


        post_title_01
        post_content_01
        page_title_01
        page_content_01
            → rendering=inline
            → inline Block markup


        no_posts_01
            → rendering=inline
            → inline Block markup


    Фактическое решение о materialization
    каждого элемента определяется
    его rendering и семантикой.

==================================================
22. BLOCK PATTERNS
==================================================

    Block Patterns являются отдельным механизмом WordPress Block Theme.

    Они материализуются в:
        patterns/

    Pattern не является новым значением semantic type Node или Composition.

    Pattern представляет собой отдельную категорию Artifact, имеющую собственные правила
        обнаружения и регистрации WordPress.

    Поддержка Patterns не должна изменять существующую систему type.

==================================================
23. STYLE VARIATIONS
==================================================

    Style Variations являются отдельным механизмом Block Theme.

    Они материализуются в:
        styles/

    Style Variation не является новым значением semantic type.

    Правила создания Style Variations принадлежат соответствующей Artifacts Architecture.

==================================================
24. ARCHITECTURAL CONSTRAINT
==================================================

    Конфигурационный пакет не должен
    описывать физические пути
    результирующих файлов Block Theme.

    Пути определяются правилами
    Block Artifacts Architecture.

    Добавление нового Node должно требовать
    только его семантической классификации
    и соответствующего rendering,
    если для данного случая уже существуют
    правила материализации.

    Добавление нового физического каталога
    должно происходить только при появлении
    новой категории Artifact,
    которую невозможно корректно разместить
    в существующих категориях.

    Semantic type не должен использоваться
    для моделирования физической структуры
    Block Theme.

==================================================
25. UNKNOWN TYPE
==================================================

    type является закрытым набором.

    Допустимые значения:

        template
        layout
        post
        page
        product
        navigation
        form
        common

    Если Node или Composition
    содержит неизвестный type:

        диагностируется ERROR

        Artifact для данного элемента
        не создаётся

        обработка остальных элементов
        продолжается

        выполнение Build в целом
        не прерывается


    Неизвестный type не должен автоматически
    преобразовываться в common
    или любой другой допустимый type.

    Ошибка Unknown Type учитывается
    в итоговом Build Status.

    Отсутствующий type и неизвестный type
    рассматриваются как ошибочные состояния.

    Node или Composition без type
    не должен получать Artifact
    до устранения ошибки конфигурации.

==================================================
26. STATUS
==================================================

    Решение принято как архитектурная основа
    для дальнейшей реализации структуры
    Block Theme Artifacts.

    Набор типов:

        template
        layout
        post
        page
        product
        navigation
        form
        common

    считается текущим минимальным набором
    и может быть пересмотрен при появлении
    новых требований.

    Block-specific правила материализации
    должны оставаться в Artifacts Layer.

    Theme Configuration и ThemeIR
    не должны содержать физические пути
    результирующей Block Theme.

theme-core v-2
NODES, COMPOSITIONS AND RENDERING
ARCHITECTURAL DESCRIPTION
(v1.0.0)

Status: Architectural Foundation

==================================================
1. PURPOSE
==================================================

    Данный документ фиксирует архитектурную модель
    Nodes, Compositions и Rendering
    в системе theme-core v-2.

    Основная цель модели:

        определить структуру элементов Theme Configuration
        отделить атомарные элементы от составных структур
        определить способ материализации элементов
        сохранить границу между декларативной моделью
            и Artifact Generation.


    Модель предназначена для построения WordPress Theme,
    соответствующей архитектуре Classic Theme
    и требованиям целевого распространения через Envato.

==================================================
2. CORE MODEL
==================================================


    Модель состоит из двух структурных сущностей:

        Node
        Composition

    Node является атомарным элементом.

    Composition является структурой,
        состоящей из Node и других Composition.

    Базовая архитектурная модель:

        Node
            ↓
        атомарный элемент

        Composition
            ↓
        Node
        Composition
        Node


    Composition не является Node.

    Composition может содержать Composition
        на произвольной глубине вложенности.


==================================================
3. NODE
==================================================


    Node представляет атомарный элемент темы.

    Node не содержит составляющих элементов.

    Node может представлять:

        конкретный визуальный элемент
        конкретный функциональный элемент
        конкретный контентный элемент
        другой атомарный элемент,
            определённый конфигурацией.

    Примеры Node:
        Site Title
        Navigation
        Copyright
        Widgets
        Post Title
        Post Content
        Page Title
        Archive Title
        Post Loop
        No Posts

    Node определяется
        собственной идентичностью и параметрами конфигурации.


==================================================
4. COMPOSITION
==================================================

    Composition представляет составную структуру.

    Composition состоит из:

        Node
        Composition

    Composition может содержать другие Composition.

    Ограничения на глубину вложенности отсутствуют.

    Пример:

        Product Card
            ├── Image
            ├── Title
            └── Button
                    ├── Icon
                    └── Label

    В данном примере:

        Image
        Title
        Icon
        Label

    являются Node.

        Button
        Product Card

    являются Composition.


==================================================
5. NODES CONFIGURATION
==================================================


    nodes.php содержит определения
        всех атомарных Node конфигурационного пакета.

    nodes.php не содержит Composition.

    Любая сущность, имеющая составляющие элементы,
        не должна регистрироваться в nodes.php
        как Node.

    Например:

        layout
        header
        footer
        sidebar
        post-loop
        index
        single
        page
        button

    не являются Node,
        если их структура определяется через дочерние элементы.


==================================================
6. COMPOSITIONS CONFIGURATION
==================================================

    compositions.php содержит определения
        всех Composition конфигурационного пакета.

    Composition может представлять:
        переиспользуемую структурную композицию
            template part
            WordPress template
            другую составную структуру.

    Примеры текущего конфигурационного пакета:

        header
        footer
        sidebar
        layout
        post-loop
        index
        single
        page
        category
        tag

    Их конкретное назначение определяется
        собственной конфигурацией Composition.


    6.1. COMPOSITION DEFAULT CHILDREN AND SLOT OVERRIDE
    --------------------------------------------------

        Composition имеет собственное объявление,
            в котором может быть определён
            набор дочерних элементов по умолчанию.

        Наличие children в объявлении Composition
            не является обязательным.

        Таким образом, Composition может иметь:

            default children

        или:

            только Resource и rendering.


        При использовании Composition
            в качестве дочернего элемента
            другой Composition
            могут быть указаны собственные children.


        Children, указанные при конкретном использовании
            Composition, являются override-набором
            для соответствующих slots.


        Правило разрешения:

            если для slot указан child
                в конкретном использовании Composition,

            используется этот child.


            если override для slot отсутствует,

            используется child
                из определения Composition.


        Таким образом:

            Composition Definition
                ↓
            default children
                ↓
            Composition Instance
                ↓
            slot overrides
                ↓
            Resolved Composition Structure


        Пример определения:

            layout
                ├── slot 1 → post-loop
                └── slot 2 → sidebar


        При использовании:

            layout
                ├── slot 1 → post-title
                ├── slot 2 → post-content
                └── slot 3 → sidebar


        результатом разрешения является:

            layout
                ├── slot 1 → post-title
                ├── slot 2 → post-content
                └── slot 3 → sidebar


        При этом:

            post-title
            post-content

        заменяют соответствующие default children
            для указанных slots.


        Если override для slot отсутствует,
            default child сохраняется.


        Если Composition не имеет
            default children,

        она может получить children
            исключительно при конкретном использовании.


        Slot override не изменяет
            исходное объявление Composition.

        Override действует только
            в пределах конкретного экземпляра
            Composition.


    6.2. COMPOSITION RESOLUTION SEMANTICS
    -------------------------------------

        Для каждого экземпляра Composition
            структура children определяется
            следующим образом:

            Composition Definition
                +
            Composition Instance Overrides
                ↓
            Resolved Children


        Resolution выполняется
            по идентификатору slot.


        Для каждого slot:

            Instance Child
                имеет приоритет

            над

            Default Child.


        Не переопределённые slots
            получают Default Child.


        Таким образом, Composition
            является переиспользуемой структурой
            с возможностью локальной специализации.


        Основной принцип:

            Default Composition
                определяет базовую структуру.

            Composition Instance
                может заменить её части
                через slot overrides.

            Исходное определение Composition
                при этом не изменяется.


==================================================
7. STRUCTURAL MODEL
==================================================


    Структура конфигурационного пакета имеет вид:

        nodes.php
            ↓
        атомарные Node

        compositions.php
            ↓
        Composition
            ↓
        Node
        Composition
        Node


    Таким образом:

        nodes.php
            описывает атомарные элементы

        compositions.php
            описывает структуры,
            построенные из этих элементов.

    Composition не должна дублироваться
        как Node только потому,
        что она может использоваться повторно.


==================================================
8. TYPE
==================================================

    Поле type присутствует
        в текущей модели конфигурационного пакета.

    Его архитектурное назначение
        на данном этапе не пересматривается.

    type не используется
        для определения способа рендеринга.

    Дополнительная ответственность type
        пока не фиксируется.

    Решение о дальнейшей роли type
        будет принято отдельно
        на последующем этапе развития модели.


==================================================
9. RENDERING
==================================================

    Способ материализации элемента не определяется полем type.

    Для этого используется отдельное поле:
        rendering

    rendering отвечает исключительно
        за способ материализации элемента
        в Theme Artifacts.

    Пример:

        type
            component

        rendering
            inline

    Таким образом:

        type
            описывает пока не определённую предметную характеристику элемента

        rendering
            определяет способ его материализации.


==================================================
10. RENDERING RESPONSIBILITY
==================================================


    rendering не определяет:
        состав элемента
        его предметное назначение
        его архитектурные связи
        структуру Composition.

    rendering определяет только:
        каким способом элемент
        должен быть представлен
        в результирующей артефакте.


==================================================
11. RENDERING VALUES
==================================================


    Для текущей версии модели
        фиксируется следующий набор rendering:

        inline
        template
        header
        footer
        sidebar
        search-form
        template-part
        comments

    Данный набор является частью
        текущей архитектурной версии.

    В старших версиях
        набор rendering может быть расширен
        или пересмотрен.


==================================================
12. INLINE RENDERING
==================================================


    rendering = inline

    означает:
        содержимое элемента
        материализуется непосредственно
        внутри текущего Artifact.

    Отдельный template file
        для такого элемента  не создаётся.


==================================================
13. TEMPLATE RENDERING
==================================================

    rendering = template

    означает:

        Composition материализуется
        как самостоятельный WordPress template file.

    Примеры:
        index.php
        single.php
        page.php
        archive.php
        category.php
        tag.php
        404.php

    Конкретное имя файла
        не является значением rendering.

    rendering определяет способ материализации,
        а идентичность Composition
        определяет конкретный Artifact.


==================================================
14. HEADER RENDERING
==================================================


    rendering = header

    означает:

        материализация в header.php
        и использование стандартной семантики
        WordPress header template.

    Подключение выполняется
        через стандартный WordPress механизм:

        get_header()


==================================================
15. FOOTER RENDERING
==================================================


    rendering = footer

    означает:

        материализация в footer.php
        и использование стандартной семантики
        WordPress footer template.

    Подключение выполняется через:

        get_footer()


==================================================
16. SIDEBAR RENDERING
==================================================


    rendering = sidebar

    означает:

        материализация в sidebar.php
        и использование стандартной семантики
        WordPress sidebar template.

    Подключение выполняется
        через:

        get_sidebar()


==================================================
17. SEARCH FORM RENDERING
==================================================


    rendering = search-form

    означает:
        использование стандартной WordPress
        search form template semantics.

    Основной стандартный механизм:

        searchform.php
        get_search_form()


==================================================
18. TEMPLATE PART RENDERING
==================================================


    rendering = template-part

    означает:

        материализация элемента
        как отдельного WordPress template part.

    Подключение выполняется
        через стандартный механизм:

        get_template_part()

    Template Part не должен без необходимости
        инлайниться в родительский Artifact.

    Это позволяет использовать
        стандартную WordPress модель
        подключения template parts.


==================================================
19. COMMENTS RENDERING
==================================================

    rendering = comments

    означает:
        материализация в comments.php
        и использование стандартной WordPress
        comments template semantics.


==================================================
20. WORDPRESS MATERIALIZATION
==================================================

    Rendering должен учитывать
        стандартную модель Classic WordPress Theme.

    В частности:

        template → самостоятельный template file

        header → header.php / get_header()

        footer → footer.php / get_footer()

        sidebar → sidebar.php / get_sidebar()

        search-form → searchform.php / get_search_form()

        template-part → отдельный template part / get_template_part()

        comments → comments.php

    Таким образом, компилятор
        не должен без необходимости
        заменять стандартные WordPress mechanisms
        прямым встраиванием содержимого.


==================================================
21. ARTIFACT GENERATION
==================================================

    Решение о способе материализации
        принимается на стадии Artifact Generation.

    Resolution не отвечает
        за конкретный способ генерации PHP.

    Resolution формирует Theme IR.

    Artifact Generation анализирует Theme IR
        и на основании rendering
        определяет способ создания Artifact.

    Архитектурная цепочка:

        Configuration
            ↓
        Theme Components
            ↓
        Theme IR
            ↓
        rendering
            ↓
        Theme Artifacts
            ↓
        WordPress Theme


==================================================
22. RESOLUTION BOUNDARY
==================================================

    Resolution не должен содержать
        WordPress-specific rendering logic.

    Resolution не должен непосредственно
        генерировать:

        get_header()
        get_footer()
        get_sidebar()
        get_template_part()
        и другие вызовы, являющиеся частью материализации Artifact.

    Resolution должен предоставить Artifact Generation
        достаточно информации для принятия этого решения.


==================================================
23. ARTIFACT GENERATION BOUNDARY
==================================================

    Artifact Generation отвечает за:

        определение способа материализации
        на основании rendering
        создание содержимого Artifact
        определение структуры результирующей темы
        применение WordPress-specific semantics.

    Artifact Generation не должен
        изменять декларативную структуру Node и Composition.


==================================================
24. ENVATO / WORDPRESS REQUIREMENT
==================================================


    Цель модели — генерировать
        полноценную WordPress Theme,
        а не произвольный набор PHP-файлов.

    Поэтому при материализации
        должны использоваться
        стандартные механизмы WordPress.

    Особенно это относится к:

        template files
        header.php
        footer.php
        sidebar.php
        searchform.php
        comments.php
        template parts.

    Это позволяет сохранять
        стандартную архитектуру WordPress Theme
        и соответствовать требованиям,
        предъявляемым к распространяемым темам.


==================================================
25. CURRENT ARCHITECTURAL MODEL
==================================================

    Текущая модель:

        Node
            ↓
        атомарный элемент

        Composition
            ↓
        структура из Node и Composition


        Node / Composition
            ↓
        rendering

        rendering
            ↓
        способ материализации

        Artifact Generation
            ↓
        Theme Artifacts

        Theme Artifacts
            ↓
        WordPress Theme


==================================================
26. ARCHITECTURAL BOUNDARIES
==================================================

    Node отвечает только за:
        представление атомарного элемента.

    Composition отвечает только за:
        описание структуры и связей между элементами.

    type отвечает:
        пока не определено;
        его дальнейшая роль
        будет определена отдельно.

    rendering отвечает только за:
        способ материализации.

    Resolution отвечает за:
        преобразование декларативной модели
        во внутреннее представление компилятора.

    Artifact Generation отвечает за:
        материализацию Theme IR в Theme Artifacts.


==================================================
27. NON-GOALS
==================================================


    Текущая модель не допускает:

        использование type для определения rendering;

        регистрацию Composition
            как Node только из-за её переиспользования;

        ограничения Composition на вложенность других Composition;

        смешивание Node и Composition;

        принятие WordPress-specific rendering decisions на стадии Resolution;

        использование технических PHP mechanisms как значений rendering,
            например:
                php
                include
                require.


==================================================
28. CURRENT DECISIONS
==================================================

    Зафиксированы следующие решения:

        1. Node является атомарным элементом.
        2. Composition является составным элементом.
        3. Composition может содержать Composition.
        4. Composition не является Node.
        5. nodes.php содержит атомарные Node.
        6. compositions.php содержит Composition.
        7. type пока не пересматривается.
        8. type не определяет rendering.
        9. rendering является отдельным полем.
        10. rendering определяет только способ материализации.
        11. Rendering decisions принимаются на стадии Artifact Generation.
        12. Для текущей версии используются:
            inline
            template
            header
            footer
            sidebar
            search-form
            template-part
            comments
        13. WordPress-specific materialization должна использовать стандартные механизмы WordPress.


==================================================
29. FINAL DEFINITION
==================================================

    Архитектурная модель Nodes,
        Compositions и Rendering
        строится вокруг строгого разделения
        структуры и материализации.

    Node:
        атомарный элемент.

    Composition:
        составная структура, содержащая Node и Composition.

    type:
        поле с пока не определённой дополнительной ответственностью.

    rendering:
        механизм определения способа материализации элемента.

    Artifact Generation:
        стадия, на которой rendering превращается
        в конкретную реализацию Artifact.

    Архитектурная формула:

        Node
        Composition
            ↓
        Theme IR
            ↓
        rendering
            ↓
        Theme Artifacts
            ↓
        WordPress Theme

    Основной принцип:

        Структура темы определяется Node и Composition.

        Способ материализации определяется rendering.

        Материализация выполняется на стадии Artifact Generation.

        WordPress Theme является физическим результатом этой материализации.

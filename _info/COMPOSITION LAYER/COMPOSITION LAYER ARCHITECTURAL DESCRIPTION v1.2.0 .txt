theme-core v-2
COMPOSITION LAYER
ARCHITECTURAL DESCRIPTION
(v1.2.0)

==================================================
1. PURPOSE
==================================================

    Composition Layer является subsystem, отвечающей за построение и разрешение object graph приложения.

    Composition Layer обеспечивает:
        - регистрацию Service Definitions
        - хранение Service Definitions (через Registry)
        - построение dependency graph
        - разрешение зависимостей
        - создание экземпляров сервисов
        - управление lifecycle стратегиями сервисов
        - сохранение runtime-экземпляров в Application Storage

    Composition Layer отвечает на вопрос:
        "Как детерминированно собрать граф объектов приложения из явных описаний?"


==================================================
2. NON-RESPONSIBILITIES
==================================================

    Composition Layer НЕ отвечает за:
        - bootstrap orchestration процесса системы
        - выполнение бизнес-логики сервисов
        - хранение runtime состояния вне процесса composition
        - логирование (как бизнес-функция)
        - диагностику (как отдельный subsystem)
        - auto-discovery сервисов
        - reflection-based analysis
        - attribute-based configuration
        - service providers
        - runtime event orchestration


==================================================
3. ARCHITECTURAL POSITION
==================================================

    Kernel
        ↓
    Bootstrap Layer
        ↓
    Composition Layer
        ↓
    Application Storage
        ↓
    Application Runtime

    Composition Layer является строго build-time + resolution-time subsystem
    и не участвует в runtime execution логике приложения.


==================================================
4. CORE PRINCIPLE
==================================================

    Composition Layer использует исключительно explicit configuration model.

    Все сервисы:
        - регистрируются вручную
        - описываются вручную
        - связываются вручную
        - разрешаются через явный graph traversal

    Система не выполняет никакого автоматического анализа кода.


==================================================
5. ARCHITECTURAL PHASE MODEL
==================================================

    Composition Layer разделяет работу на две фазы.


5.1 BUILD PHASE
==================================================

        Отвечает за:
            - регистрацию Service Definitions
            - валидацию definitions
            - построение dependency graph

        Результат:
            - immutable graph description

        Важно:
            - никаких объектов сервисов не создаётся


    5.2 RESOLUTION PHASE
    ==================================================

        Отвечает за:
            - eager resolution
            - lazy resolution
            - transient resolution
            - создание экземпляров сервисов
            - разрешение зависимостей
            - применение lifecycle стратегии
            - взаимодействие с Application Storage

        Результат:
            - готовые runtime service instances

==================================================
6. SUPPORTED FEATURES
==================================================

    Composition v1.2 поддерживает:

        - Service Definitions
        - Service Registry
        - Dependency Graph
        - Dependency Graph Builder
        - Dependency Resolver
        - Service Factory
        - Lifecycle Manager
        - Service Composer
        - Resolution Context
        - Eager Services
        - Lazy Services
        - Transient Services

==================================================
7. EXPLICIT RESTRICTIONS
==================================================

    Composition v1.2 НЕ поддерживает:

        - Reflection
        - Autowiring
        - Attributes
        - Auto Discovery
        - Auto Registration
        - Service Providers
        - Service Tags
        - Service Aliases
        - Service Decoration
        - Container Compilation
        - Hidden internal state outside Resolution Context

==================================================
8. CORE CONCEPTS
==================================================

    8.1 Service
    ==================================================

        Service представляет собой обычный PHP объект,
        используемый системой во время runtime.

        Примеры:
            - Configuration
            - StructuredLogger
            - DiagnosticsService


    8.2 Service Definition
    ==================================================

        Service Definition является immutable описанием сервиса.

        Definition содержит:
            - service identifier
            - service class
            - lifecycle type
            - dependency list

        Definition НЕ содержит:
            - instance
            - runtime state

        Definition является compile-time metadata.


    8.3 Service Identifier
    ==================================================

        Service Identifier является уникальным строковым ключом,
            используемым для поиска Service Definition.

        В Composition v1.2 в качестве identifier используется
            полное имя класса или интерфейса.

        Примеры:
            Configuration::class
            LoggerInterface::class
            DiagnosticsService::class

        Identifier обязан быть уникальным в пределах Registry.

        Повторная регистрация identifier запрещена.


    8.4 Service Registry
    ==================================================

        Service Registry является хранилищем Service Definitions.

        Registry отвечает за:
            - регистрацию definitions
            - получение definitions
            - проверку существования definitions

        Registry не участвует в runtime resolution.


    8.5 Dependency Graph
    ==================================================

        Dependency Graph является immutable моделью связей сервисов.

        Он строится в BUILD PHASE и содержит:
            - nodes (services)
            - edges (dependencies)

        Graph используется только для resolution planning.


    8.6 Dependency Graph Builder
    ==================================================

        Dependency Graph Builder отвечает за построение
        Dependency Graph на основании зарегистрированных
        Service Definitions.

        Builder выполняет:
            - анализ definitions
            - построение nodes
            - построение dependency edges
            - формирование immutable graph model

        Builder работает только в BUILD PHASE.


    8.7 Resolution Context
    ==================================================

        Resolution Context является явным runtime state контейнером
        для процесса построения object graph.

        Он содержит:
            - currently constructed instances
            - resolving stack

        Resolution Context НЕ является Application Storage.


    8.8 Service Factory
    ==================================================

        Service Factory отвечает исключительно за создание объекта.

        Factory получает:
            - service class
            - resolved dependencies

        Factory:
            - НЕ знает Registry
            - НЕ знает Graph
            - НЕ знает Lifecycle
            - НЕ хранит state


    8.9 Lifecycle Manager
    ==================================================

        Lifecycle Manager отвечает за применение lifecycle политики.

        Lifecycle Manager определяет:
            - должен ли сервис быть сохранён
            - должен ли сервис быть переиспользован
            - должен ли сервис создаваться повторно

        Lifecycle Manager не создаёт объекты
            и не выполняет dependency resolution.


    8.10 Service Composer
    ==================================================

        Service Composer является orchestration layer RESOLUTION PHASE.

        Composer отвечает за:
            - traversal dependency graph
            - управление Resolution Context
            - orchestration of Dependency Resolver
            - orchestration of Service Factory
            - application of lifecycle rules
            - persistence into Application Storage

        Composer НЕ хранит permanent state вне Resolution Context.

==================================================
9. APPLICATION INTEGRATION MODEL
==================================================

    Application является единственной публичной точкой доступа
    к сервисам во время runtime.

    Runtime взаимодействует только с Application.

    Application владеет:
        - Application Storage
        - Service Composer

    Service Composer использует:
        - Registry
        - Graph
        - Factory
        - Lifecycle Manager

    Общая схема:

        Runtime
            ↓
        Application
            ↓
        Composer
            ↓
        Registry
            ↓
        Graph
            ↓
        Factory
            ↓
        Lifecycle

==================================================
10. DEPENDENCY RESOLUTION MODEL
==================================================

    Dependencies описываются явно в Service Definition.

    Resolution выполняется через graph traversal:

        A → B → C

    Алгоритм:
        - Composer запрашивает Definition
        - строит path в graph
        - проверяет cycles через Resolution Context stack
        - рекурсивно резолвит зависимости
        - передаёт готовый dependency set в Factory

==================================================
11. CYCLE HANDLING STRATEGY
==================================================

    Composition Layer обязан обнаруживать циклы:

        if service appears twice in Resolution Context stack:
            → throw CompositionCycleException

    Partial construction НЕ допускается.

    Объекты всегда либо:
        - полностью построены
        - либо не созданы

==================================================
12. SERVICE LIFECYCLE
==================================================

    12.1 Eager
    ==================================================

        - создаётся во время startup resolution
        - сохраняется в Application Storage
        - может участвовать в early dependency resolution


        ==================================================
        12.1.1 STARTUP PHASE
        ==================================================

            Startup Phase отвечает за выполнение
            процедур запуска Composition Runtime.

            Startup Phase обеспечивает:

                1. Выполнение Bootstrap Pipeline.
                2. Последовательное выполнение всех
                зарегистрированных Bootstrap Steps.
                3. Подготовку Composition Runtime
                к дальнейшей работе.

            Startup Phase не создаёт сервисы напрямую.

            Startup Phase является координатором
            процесса запуска системы.


        ==================================================
        12.1.2 BOOTSTRAP PIPELINE
        ==================================================

            Bootstrap Pipeline представляет собой
            последовательность Bootstrap Steps,
            выполняемых во время Startup Phase.

            Pipeline обеспечивает:

                1. Определённый порядок запуска.
                2. Изоляцию отдельных этапов запуска.
                3. Возможность расширения процесса
                инициализации системы.

            Каждый Bootstrap Step выполняет
            одну специализированную задачу.


        ==================================================
        12.1.3 EAGER BOOTSTRAP STEP
        ==================================================

            Eager Bootstrap Step отвечает за
            инициализацию всех eager сервисов.

            Eager Bootstrap Step:

                1. Получает список eager сервисов.
                2. Формирует план инициализации.
                3. Определяет корректный порядок
                создания сервисов.
                4. Создаёт экземпляры eager сервисов.
                5. Гарантирует завершение их
                инициализации до начала работы
                Composition Runtime.

            Eager Bootstrap Step не участвует
            в обработке lazy сервисов.

            Для построения порядка инициализации
            используются Dependency Plan Builder
            и Dependency Graph.


    12.2 Lazy
    ==================================================

        - создаётся при первом request
        - результат сохраняется в Application Storage
        - повторно используется


    12.3 Transient
    ==================================================

        - создаётся при каждом request
        - НЕ сохраняется в Application Storage

==================================================
13. STORAGE MODEL
==================================================

    Результатом работы Composition Layer является CompositionRuntime
        который предоставляет доступ к собранному сервисному окружению
        через ServiceComposer

    Результат работы Composition должен быть доступен на слое EXECUTION RUNTIME


==================================================
14. BOOTSTRAP FLOW
==================================================

    Kernel
        ↓
    Bootstrap Layer
        ↓
    Composition Bootstrapper
        ↓
    Register Service Definitions
        ↓
    Build Dependency Graph
        ↓
    Start Resolution Phase
        ↓
    Resolve Eager Services
        ↓
    Store Services In Application Storage
        ↓
    Runtime

==================================================
15. LAZY RESOLUTION FLOW
==================================================

    Runtime
        ↓
    Request Service
        ↓
    Application
        ↓
    Service Composer
        ↓
    Load Definition
        ↓
    Resolve Dependency Graph Path
        ↓
    Create Resolution Context
        ↓
    Service Factory
        ↓
    Create Service
        ↓
    Store In Application Storage
        ↓
    Return Instance

==================================================
16. RESOLUTION FAILURE STRATEGY
==================================================

    Composition Layer использует fail-fast подход.

    При возникновении ошибок процесс resolution
    немедленно прерывается.

    Поддерживаются следующие исключения.


    16.1 CompositionDefinitionNotFoundException
    ==================================================

        Выбрасывается если Service Definition отсутствует в Registry.


    16.2 CompositionCycleException
    ==================================================

        Выбрасывается если обнаружена циклическая зависимость во время graph traversal.


    16.3 CompositionInstantiationException
    ==================================================

        Выбрасывается если Service Factory не смог создать экземпляр сервиса.

==================================================
17. DESIGN GOAL
==================================================

    Composition Layer должен оставаться:
        - explicit
        - deterministic
        - stateless (outside Resolution Context)
        - graph-driven
        - predictable

    Composition Layer не должен становиться framework container'ом.

    Основная цель:
        "Сборка системы как явного графа объектов без скрытого поведения и магии."

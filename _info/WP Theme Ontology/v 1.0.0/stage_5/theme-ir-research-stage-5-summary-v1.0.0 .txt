theme-core v-2
THEME IR RESEARCH
STAGE 5
SCENARIOS-FIRST APPROACH
(v1.0.0)

Status: Completed

==================================================
1. PURPOSE
==================================================

    Определить практическое направление дальнейшего
    исследования Theme IR.

    Требовалось отказаться от проектирования модели
    ради модели и сформировать методику, позволяющую
    вывести архитектуру Theme IR из объективных
    требований генераторов артефактов.

==================================================
2. INITIAL POSITION
==================================================

    К началу данного этапа исследования уже был
    установлен главный архитектурный вывод.

        Theme IR существует для устранения сильной
        связанности между ThemeComponents и
        генераторами артефактов.

    Следовательно, дальнейшее исследование должно
    было определить, каким образом должен строиться
    стабильный контракт Theme IR.

==================================================
3. RESEARCH GOAL
==================================================

    В качестве новой цели исследования было принято
    следующее положение.

        Определить минимальную архитектуру слоя
        Theme IR, которая обеспечивает стабильный
        контракт между ThemeComponents и
        генераторами артефактов, полностью устраняет
        их сильную связанность и создаёт единую
        точку для выполнения общей
        архитектурно-независимой подготовки модели,
        пригодной для повторного использования
        генераторами.

==================================================
4. FIRST DISCOVERY
==================================================

    Было установлено, что стабильность контракта не
    может достигаться копированием внутренней модели
    ThemeComponents.

    Если Theme IR повторяет структуру внутренних
    доменов, то любое изменение этой структуры
    приводит к изменению контракта и, как следствие,
    к изменению генераторов.

    Следовательно,

        стабильный контракт должен строиться вокруг
        инвариантов предметной области, а не вокруг
        текущей структуры ThemeComponents.

==================================================
5. SECOND DISCOVERY
==================================================

    Далее был рассмотрен вопрос, относительно чего
    вообще должен строиться публичный контракт
    Theme IR.

    Исследование показало, что генераторы не
    заинтересованы во внутреннем устройстве
    ThemeComponents.

    Их интересуют исключительно задачи,
    необходимые для построения конечных
    артефактов.

    Следовательно,

        контракт Theme IR должен быть ориентирован
        на задачи генераторов, а не на устройство
        ThemeComponents.

    Иначе говоря,

        публичный API Theme IR должен отвечать
        на вопросы генератора,

        а не предоставлять внутренние объекты
        системы.

==================================================
6. METHODOLOGICAL CHANGE
==================================================

    На предыдущих этапах предпринимались попытки
    определить:

        - какие сущности должны существовать;
        - какие коллекции необходимо хранить;
        - какие модели следует экспортировать.

    Подобный подход вновь приводил к построению
    архитектуры ради самой архитектуры.

    Поэтому направление исследования было изменено.

    Вместо вопроса

        "Какие сущности должны входить
         в Theme IR?"

    исследование должно отвечать на вопрос

        "Какой полный набор сценариев должен
         поддерживать любой генератор
         артефактов?"

==================================================
7. NEW RESEARCH PRINCIPLE
==================================================

    После определения полного набора сценариев
    появляется возможность задать следующий вопрос.

        "Какая минимальная архитектура Theme IR
         способна реализовать данные сценарии?"

    Таким образом архитектура Theme IR должна
    становиться следствием требований генераторов,
    а не наоборот.

==================================================
8. WORKING HYPOTHESIS
==================================================

    На основании проведённого анализа была
    сформулирована новая рабочая гипотеза.

    Theme IR представляет собой не просто
    стабильный контракт между ThemeComponents
    и генераторами.

    Theme IR является этапом подготовки единой
    предметной модели, уже приведённой в состояние,
    для повторного использования различными генераторами.

    Такой подход одновременно:

        - устраняет сильную связанность;
        - создаёт единую точку общей подготовки
          модели;
        - позволяет централизованно выполнять
          повторно используемые вычисления;
        - естественным образом поддерживает
          индексацию, кэширование и другие
          архитектурно-независимые оптимизации.

==================================================
9. RESULT OF THE STAGE
==================================================

    Главным результатом данного этапа стало
    изменение направления исследования.

    Вместо проектирования структуры Theme IR
    исследование перешло к определению полного
    набора сценариев, которые должен поддерживать
    любой генератор артефактов.

    Именно эти сценарии должны стать объективным
    критерием проектирования публичного контракта
    Theme IR.

    После их определения станет возможным
    спроектировать минимальную архитектуру
    Theme IR, достаточную для реализации всех
    выявленных сценариев и одновременно
    обеспечивающую независимость генераторов
    от внутренней модели ThemeComponents.


==================================================
10. IMPORTANT IDEAS 
==================================================


    Стабильный контракт должен строиться вокруг инвариантов предметной области, 
        а не вокруг текущей структуры ThemeComponents.

    Контракт Theme IR должен быть ориентирован на задачи генераторов, 
        а не на устройство ThemeComponents. То есть публичный API Theme IR должен отвечать 
        на вопросы генератора, а не предоставлять ему внутренние объекты системы

    Нужно искать полный набор сценариев, которые должен поддерживать любой генератор, А уже затем определить: 
        -какая модель лучше всего реализует эти сценарии?
        -какую минимальную архитектуру должен иметь Theme IR, чтобы поддержать эти сценарии?
    
    Theme IR — это не просто стабильный контракт. Это этап подготовки единой предметной модели, 
        уже приведённой в состояние, максимально удобное для любых генераторов.

theme-core v-2
THEME IR RESEARCH
STAGE 7
GENERATOR CONTRACT ANALYSIS
(v1.0.0)

Status: Completed

==================================================
1. PURPOSE
==================================================

   Начать практическое применение ранее
   сформированной методологии исследования.

   Исследовать реальные потребности генераторов
   артефактов на примере Classic Architecture
   и определить первые объективные требования
   к публичному контракту Theme IR.

==================================================
2. INITIAL POSITION
==================================================

    Предыдущий этап завершил формирование методологии исследования.

    Было принято решение отказаться от непосредственного проектирования Theme IR.

    Вместо этого исследование должно последовательно анализировать реальные генераторы артефактов.

    Для каждого генератора задаётся единственный вопрос:

        "Какие данные он должен получить от Theme IR, чтобы полностью выполнить свою задачу?"

==================================================
3. FIRST PRACTICAL DECISION
==================================================

    В качестве первой исследуемой архитектуры выбрана Classic WordPress Theme.

    Причины выбора:
        - наиболее зрелая архитектура;
        - минимальное количество архитектурной специфики;
        - хороший фундамент для дальнейшего исследования Hybrid и Block Theme.

==================================================
4. IMPORTANT TERMINOLOGY
==================================================

    Было установлено, что объектом исследования должны быть не файлы темы, а логические артефакты.
        например functions.php не является логическим артефактом. Он представляет собой лишь физический контейнер 
        нескольких независимых результатов генерации.

        Примеры логических артефактов:
            - Theme Supports;
            - Navigation Menus;
            - Widget Areas;
            - Image Sizes;
            - Assets Registration;
            - Assets Enqueue;
            - Editor Styles.

    Каждый из них имеет собственную ответственность и собственные требования к Theme IR.

==================================================
5. LOGICAL ARTIFACT CRITERIA
==================================================

    Были сформулированы критерии выделения самостоятельного логического артефакта.

    Артефакт существует только тогда, когда одновременно выполняются следующие условия.
        1. Имеет самостоятельную цель.
        2. Требует собственного набора  предметных данных.
        3. Может быть полностью сгенерирован независимо от остальных артефактов.

==================================================
6. RESEARCH OBJECT
==================================================

    Было уточнено, что объектом исследования является не минимальная WordPress Theme.

    Исследуется полностью реализованная production-ready Classic Theme,
        не требующая ручного программирования после генерации.

    Это позволяет исследовать именно целевую архитектуру платформы, а не минимально допустимую тему.

==================================================
7. RESPONSIBILITY AREAS
==================================================

    Был введён дополнительный уровень декомпозиции исследования.

        Architecture
            ↓
        Responsibility Areas
            ↓
        Logical Artifacts
            ↓
        Artifact Generators
            ↓
        Theme IR Scenarios

    При этом было установлено, что Responsibility Areas не являются частью архитектуры Theme Core.

    Они существуют исключительно как исследовательский инструмент, позволяющий систематически
        декомпозировать архитектуру на логические артефакты.

==================================================
8. RESEARCH BOUNDARIES
==================================================

    Было принято решение исследовать исключительно архитектуру темы, а не прикладную функциональность.

    Поэтому в область исследования входят:
        - Theme Supports;
        - Navigation Menus;
        - Widget Areas;
        - Templates;
        - Template Parts;
        - Assets;
        - Styles;
        - Scripts;
        - другие архитектурные элементы темы.

    Прикладная функциональность сознательно исключается.

        Например:
            - Custom Post Types;
            - REST API;
            - Shortcodes;
            - WooCommerce-логика;
            - SEO;
            - Forms;
            - прочая бизнес-логика темы.

==================================================
9. FIRST ARTIFACT ANALYSIS
==================================================

    Первым исследованным логическим артефактом стал Theme Supports.

    Было установлено, что генератору требуется не PHP-код и не API WordPress,
        а предметная информация о поддерживаемых возможностях темы.

    Анализ показал, что каждая поддержка естественным образом представляется предметной сущностью.

        ThemeSupport
            id
            configuration

    Theme IR не обязан знать смысл отдельных возможностей WordPress.

    Он предоставляет генератору декларации возможностей, 
        а генератор самостоятельно материализует их в вызовы add_theme_support().

==================================================
10. SECOND ARTIFACT ANALYSIS
==================================================

    Для проверки найденной закономерности был исследован генератор Navigation Menus.

    Было установлено, что он также работает не с API WordPress, а с предметными сущностями.

        NavigationMenu
            id
            title

    Генератор самостоятельно преобразует их в вызовы register_nav_menus().

    Таким образом, одна и та же модель взаимодействия повторилась для двух независимых генераторов.

==================================================
11. FIRST ENGINEERING PATTERN
==================================================

    В ходе сравнения первых генераторов была обнаружена первая повторяющаяся
        инженерная закономерность.

    Theme IR предоставляет генератору не параметры функций WordPress,
        а предметные сущности.

    Генератор отвечает исключительно за преобразование этих сущностей
        в целевую архитектуру.

==================================================
12. TEMPLATE ANALYSIS
==================================================

    Для проверки закономерности был рассмотрен генератор шаблонов.

    Несмотря на совершенно иной результат генерации, принцип взаимодействия оказался тем же самым.

    Генератор работает не с PHP-файлом, а с предметной моделью шаблона.

        Например:
            Template
                Composition
                    Regions
                        Components

    После получения модели генератор самостоятельно преобразует 
        её в соответствующее представление целевой архитектуры.

==================================================
13. ARCHITECTURAL INDEPENDENCE
==================================================

    В результате анализа было получено практическое определение
        архитектурной независимости Theme IR.

    Theme IR является архитектурно независимым тогда, когда его публичный
        контракт состоит исключительно из предметных сущностей, а не отражает API конкретной платформы.

==================================================
14. GENERATOR CONTRACT
==================================================

    Было установлено, что генератор никогда не заинтересован во всём Theme IR.

    Каждый генератор заинтересован исключительно в собственной законченной предметной модели.
        Например:
            - Theme Supports Model;
            - Navigation Menus Model;
            - Template Model;
            - Assets Model.

    Это привело к гипотезе, что публичный контракт Theme IR должен проектироваться
        вокруг специализированных моделей, а не вокруг единого объекта,
        содержащего всю предметную информацию.

==================================================
15. PREPARED CONSUMPTION MODEL
==================================================

    Одним из важнейших результатов исследования стало различие между
        моделью хранения и моделью потребления.

    Было установлено, что генератор не должен выполнять:
        - поиск объектов;
        - разрешение ссылок;
        - навигацию по Theme IR;
        - построение графов;
        - вычисление зависимостей.

    Всё это относится к ответственности Theme IR.

    Генератор должен получать полностью подготовленную предметную модель,
        достаточную для непосредственной генерации артефакта.

==================================================
16. CONTRACT COMPLETENESS CRITERION
==================================================

    Был сформулирован новый инженерный критерий качества
        публичного контракта Theme IR.

    Если генератор вынужден самостоятельно:

        - искать объекты;
        - разрешать связи;
        - вычислять зависимости;
        - подготавливать модель;

    то публичный контракт Theme IR является недостаточным.

    Генератор должен получать уже подготовленную модель, полностью готовую к генерации.

==================================================
17. MATERIALIZATION BOUNDARY
==================================================

    Было подтверждено ранее сделанное разделение ответственности.

    Theme IR ничего не знает о способе материализации.

    Он предоставляет исключительно предметную модель.

    Генератор самостоятельно преобразует её:
        - в PHP;
        - HTML;
        - CSS;
        - JSON;
        - либо в любую другую архитектурную форму.

==================================================
18. FUNDAMENTAL PRINCIPLE
==================================================

    Главным результатом данного этапа стало формирование нового принципа
        проектирования Theme IR.

        Публичный контракт Theme IR должен состоять не из объектов
            хранения, а из объектов потребления.

    Иными словами, Theme IR обязан предоставлять каждому генератору именно ту
        законченную предметную модель, которая необходима для выполнения его задачи.

    Внутренняя организация Theme IR при этом не имеет значения.

==================================================
19. RESULT OF THE STAGE
==================================================

    Исследование впервые позволило перейти от общих архитектурных
        рассуждений к анализу конкретных контрактов между Theme IR
        и генераторами артефактов.

    Было подтверждено, что проектирование Theme IR должно выполняться
        исключительно с точки зрения потребителей его данных.

    Theme IR не моделирует API WordPress.

    Он моделирует предметную область, предоставляя генераторам полностью
        подготовленные предметные модели, готовые к непосредственной генерации.

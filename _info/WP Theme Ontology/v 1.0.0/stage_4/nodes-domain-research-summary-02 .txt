theme-core v-2
NODES DOMAIN RESEARCH
SUMMARY
(v2.0.0)

Status: Research Completed

==================================================
1. PURPOSE
==================================================

    Целью исследования являлось определение
    минимальной, но достаточной модели данных
    домена Nodes, позволяющей компилятору
    автоматически определять способ обработки
    каждого Node в процессе построения темы.

    Исследование носило исключительно прикладной
    характер.

    Основной задачей являлось не построение
    абстрактной классификации Node, а разработка
    модели, пригодной для использования
    в pipeline theme-core v-2.

==================================================
2. INITIAL HYPOTHESIS
==================================================

    Первоначально предполагалось, что каждый
    Node должен содержать минимальный набор
    информации:

        - id;
        - type;
        - path.

    В процессе исследования модель была
    значительно расширена.

==================================================
3. NODE MODEL
==================================================

    Было принято решение разделить свойства Node
    на обязательные и необязательные.

--------------------------------------------------
Required Properties
--------------------------------------------------

    Каждый Node обязан содержать:

        id

            Уникальный идентификатор Node.

        path

            Путь к директории Node,
            содержащей все его ресурсы.

        name

            Человекочитаемое имя Node.

    Отсутствие любого из перечисленных полей
    делает Node невалидным.

--------------------------------------------------
Optional Properties
--------------------------------------------------

    Node может дополнительно содержать:

        description

            Текстовое описание Node.

        capabilities

            Список поддерживаемых возможностей.

        metadata

            Произвольные пользовательские данные.

    Данные поля являются полностью
    необязательными.

==================================================
4. NODE TYPE
==================================================

    В ходе исследования было принято решение
    сохранить обязательное поле:

        type

    Данное поле не описывает внешний вид Node.

    Также оно не является классификацией
    пользовательского интерфейса.

    Единственное назначение поля type —
    определить семейство обработчиков,
    которое должно использоваться
    компилятором.

==================================================
5. PROCESSING MODEL
==================================================

    Было установлено, что различные Node могут
    требовать различных способов обработки.

    Однако принято решение не помещать описание
    алгоритма обработки непосредственно
    внутрь Node.

    Вместо этого каждый тип Node определяет
    собственную стратегию обработки.

==================================================
6. TYPE STRATEGY
==================================================

    Для каждого типа Node вводится понятие
    стратегии обработки.

    Каждый тип обязан содержать поле:

        strategy

    По умолчанию стратегия имеет значение:

        default

    Это означает использование стандартного
    обработчика данного типа.

==================================================
7. STRATEGY OVERRIDE
==================================================

    Несмотря на наличие стратегии по умолчанию,
    отдельные Node могут требовать
    нестандартной обработки.

    Для этого принято решение разрешить
    переопределение стратегии
    непосредственно в описании Node.

    Например:

        type:
            name: component
            strategy: custom

    Таким образом,

        сначала определяется тип Node,

        затем выбирается стратегия,
        принадлежащая данному типу,

        после чего, при необходимости,
        стратегия может быть переопределена
        самим Node.

==================================================
8. ARCHITECTURAL BENEFITS
==================================================

    Принятое решение обеспечивает:

        - простую минимальную модель Node;

        - обязательную валидацию критически
          важных полей;

        - возможность документирования Node;

        - расширяемость модели без нарушения
          обратной совместимости;

        - единый механизм выбора обработчика;

        - возможность локального переопределения
          поведения отдельных Node;

        - отсутствие необходимости изменять
          архитектуру pipeline при появлении
          нестандартных случаев.

==================================================
9. FINAL ARCHITECTURAL DECISION
==================================================

    Итоговая модель Node состоит из двух уровней.

    Первый уровень описывает сам Node
    как ресурс темы.

    Второй уровень определяет способ
    обработки Node посредством его типа.

    Стандартная стратегия определяется типом.

    При необходимости конкретный Node может
    переопределить её собственной настройкой.

==================================================
10. RESEARCH COMPLETION CRITERION
==================================================

    Исследование считается завершённым.

    Минимальная модель данных домена Nodes
    определена.

    Определены обязательные и необязательные
    свойства Node.

    Принята модель обработки Node через типы
    с поддержкой переопределяемых стратегий.

    Дальнейшая работа должна быть направлена
    на проектирование системы типов Node
    и реализации соответствующих обработчиков
    в pipeline theme-core v-2.

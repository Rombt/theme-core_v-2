ARTIFACT DOMAIN
ARCHITECTURAL DESCRIPTION
(v1.0.0)

Status: Architectural Target

==================================================
1. PURPOSE
==================================================

    Artifact Domain является центральным доменом управления результатами сборки.

    Artifact Domain предоставляет единую модель представления всех результатов генерации
        независимо от способа их последующей материализации.

    Artifact Domain отделяет процесс создания
        результата от процесса его физического представления.

==================================================
2. PROBLEM
==================================================

    Бизнес-процессы сборки создают результаты,
        которые в дальнейшем должны быть сохранены, опубликованы или преобразованы.

    Прямая работа с файловой системой приводит к:
        смешению бизнес-логики и инфраструктуры
        невозможности тестирования генерации без файловой системы
        сильной связанности между генераторами и механизмами вывода
        ограничению будущих способов публикации результатов

    Необходим промежуточный архитектурный слой.

==================================================
3. CORE PRINCIPLE
==================================================

    Artifact является основной единицей результата в системе.

    Pipeline работает с Artifact.
    Runtime работает с Artifact.
    Build Session хранит Artifact.
    Writers материализуют Artifact.

    Генераторы не работают с файловой системой.

==================================================
4. ARCHITECTURAL FORMULA
==================================================

    Business Logic
            ↓
        Artifact
            ↓
    Physical Representation

    Artifact является границей между доменной моделью и инфраструктурой.

==================================================
5. ARTIFACT
==================================================

    Artifact представляет собой результат выполнения системы.

    Artifact не является файлом.

    Artifact не зависит от файловой системы.

    Artifact является архитектурным объектом.

==================================================
6. ARTIFACT IDENTITY
==================================================

    Каждый Artifact обладает уникальной идентичностью внутри Build Session.

    Идентичность должна быть стабильной на протяжении всей сборки.

    Примеры:
        theme-json
        style-css
        functions-php
        screenshot

==================================================
7. ARTIFACT TYPE
==================================================

    Каждый Artifact обладает типом.

    Тип описывает архитектурную природу результата.

    Минимальный набор типов определяется конкретной реализацией.

    Возможные примеры:
        FILE
        DIRECTORY
        PACKAGE
        ARCHIVE
        RESOURCE

==================================================
8. ARTIFACT CONTENT
==================================================

    Artifact содержит полезное содержимое, созданное бизнес-логикой.

    Формат содержимого не ограничивается.

        Примеры:
            text
            json
            php source
            css source
            binary data

==================================================
9. ARTIFACT DESTINATION
==================================================

    Artifact может содержать информацию о предполагаемом месте материализации.

    Destination не является файловой системой.

    Destination представляет собой логическую цель публикации результата.

    Примеры:
        theme.json
        assets/style.css
        inc/setup.php

==================================================
10. ARTIFACT METADATA
==================================================

    Artifact может содержать дополнительные метаданные.

    Метаданные не участвуют в идентичности артефакта.

    Примеры:
        generator information
        timestamps
        build attributes
        publication hints

==================================================
11. ARTIFACT COLLECTION
==================================================

    Artifact Collection представляет собой контейнер артефактов Build Session.

    Collection является владельцем Artifact Domain внутри сборки.

    Collection обеспечивает операции:
        add
        replace
        remove
        get
        has
        all
        count

==================================================
12. ARTIFACT LIFECYCLE
==================================================

    Artifact проходит последовательность стадий.

        Created
            ↓
        Modified
            ↓
        Published
            ↓
        Archived

    Конкретная реализация может поддерживать только часть состояний.

==================================================
13. ARTIFACT OWNERSHIP
==================================================

    Artifact всегда принадлежит Build Session.

    Runtime управляет жизненным циклом Build Session.

    Следовательно Runtime косвенно управляет жизненным циклом Artifact.

==================================================
14. BUILD SESSION INTEGRATION
==================================================

    Build Session является владельцем Artifact Collection.

    Модель хранения:

        Build Session
            └── Artifact Collection
                    ├── Artifact
                    ├── Artifact
                    ├── Artifact
                    └── Artifact

==================================================
15. PIPELINE INTEGRATION
==================================================

    Pipeline работает через Artifact Collection.

    Stage может:
        создавать артефакты
        изменять артефакты
        удалять артефакты
        анализировать артефакты

    Stage не работает напрямую с файловой системой.

==================================================
16. WRITER INTEGRATION
==================================================

    Writer является потребителем артефактов.

    Writer получает Artifact Collection и создаёт физическое представление.

    Writer не изменяет Artifact.

    Writer не создаёт Artifact.

==================================================
17. MULTIPLE REPRESENTATIONS
==================================================

    Один и тот же Artifact может быть материализован различными способами.

    Примеры:

        Artifact
            ↓
          File

        Artifact
            ↓
        Zip Package

        Artifact
            ↓
        Remote Storage

        Artifact
            ↓
        Memory Export

==================================================
18. DOMAIN BOUNDARY
==================================================

    Artifact Domain не отвечает за:
        генерацию артефактов
        файловую систему
        запись файлов
        архивирование
        публикацию
        транспортировку

    Artifact Domain отвечает только за моделирование результатов сборки.

==================================================
19. FUTURE EXTENSIONS
==================================================

    Домен должен поддерживать возможность дальнейшего расширения без изменения
        базовой архитектуры.

    Возможные расширения:

        Artifact Manifest
        Artifact Relations
        Artifact Dependencies
        Artifact Versioning
        Artifact Provenance
        Artifact Validation
        Artifact Packaging

==================================================
20. ARCHITECTURAL GOAL
==================================================

    Artifact Domain должен стать единым источником истины 
        для всех результатов Build Pipeline.

    Любой результат сборки должен существовать в системе сначала как Artifact и только
        затем как физическое представление.

==================================================
21. FINAL DEFINITION
==================================================

    Artifact Domain предоставляет унифицированную модель представления результатов компиляции.

    Центральным объектом домена является: Artifact

    Центральным контейнером домена является: Artifact Collection

    Центральным принципом домена является: Artifact First

    Все результаты Build Pipeline должны существовать как Artifact до момента
        их материализации инфраструктурным слоем.

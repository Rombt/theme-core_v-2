roadmap интеграции домена Nodes в слой Theme Components: 
++ Привести модель Node в соответствие со спецификацией 
    ++ добавить обязательное поле resource;
    ++ определить модель NodeType вместо использования массива type. 
++ Завершить модель домена Nodes 
    ++ реализовать NodeType;
    ++ реализовать модель стратегии обработки (strategy);
    ++ обеспечить переопределение стратегии на уровне Node. 
++ Реализовать полноценный ResourceResolver 
    ++ разрешение логического resource;
    ++ поиск ресурсов по соглашениям (Convention over Configuration);
    ++ возврат корректного ResolvedResource. 
Интегрировать ResourceResolver в NodesComponentBuilder разрешить ресурсы для каждого Node;
    выполнить обязательную проверку существования ресурсов;
    сформировать готовую модель для следующих стадий pipeline. 
Валидацию домена Nodes должна оставаться заглушкой на данном этапе. 
Интегрировать Nodes с Composition Composition 
    должен использовать только зарегистрированные Nodes;
    запретить создание Composition из несуществующих Nodes. 
Подготовить инфраструктуру для последующих стадий 
    чтобы Render Preparation и Materialization работали уже с разрешёнными Node и их ресурсами, а не с конфигурацией напрямую. 
пункты обозначенные ++ уже выполнены.



Интегрировать Nodes с Composition Composition:
+- Этап 1. Подготовить модель Composition
    ++ 1.1. Расширить CompositionNode
        Добавить ссылку на зарегистрированный Node.
        В результате CompositionNode сможет ссылаться:
        на вложенную Composition;
        на зарегистрированный Node.
        Например:
            CompositionNode
                ├── id
                ├── children
                ├── composition?
                └── node?
        Добавить методы:
        referencesNode(): bool
        node(): ?Node
        setNode(Node $node): void
    отложено 1.2. Определить инвариант CompositionNode
        После завершения построения компонента каждый CompositionNode обязан удовлетворять одному из условий:
        composition != null
        или
        node != null
        Третьего варианта быть не должно.
        Пока это можно обеспечить логикой Builder, без отдельного валидатора.
++ Этап 2. Подготовить Nodes для поиска
    Сейчас NodeCollection уже существует.
    Нужно убедиться, что она предоставляет быстрый поиск
    find(string $id): ?Node
    Если метод уже есть — ничего делать не нужно.
    Если нет — добавить.
    Это полностью соответствует роли коллекции.
++ Этап 3. Изменить CompositionCollectionBuilder Это основной этап.
    ++ 3.1. Добавить зависимость
        Builder должен получать
        NodeCollection
        наряду с
        CompositionCollection
        Теперь Builder сможет разрешать ссылки обоих типов.
    ++ 3.2. Изменить алгоритм третьего прохода
        Вместо
        resolve Composition
        должно стать
        resolve Composition
        если нет
        resolve Node
        если нет
        Exception
        То есть:
        CompositionNode(id)
                │
                ▼
        Composition ?
                │
            yes
                │
        setComposition()
                │
            no
                ▼
        Node ?
                │
            yes
                │
        setNode()
                │
            no
                ▼
        UnknownReferenceException
    ++ 3.3. Рекурсивное разрешение остаётся прежним
        Метод
        resolveReferences()
        по-прежнему обходит дерево рекурсивно.
        Меняется только логика поиска.
++ Этап 4. Добавить специализированное исключение
    Вместо
    RuntimeException
    лучше сделать отдельное исключение.
    Например
    UnknownCompositionNodeReferenceException
    или
    CompositionReferenceNotFoundException
    Оно должно сообщать:
    Composition;
    неизвестный id;
    путь (если позже понадобится).
++ Этап 5. Рефакторинг инфраструктуры Theme Components
    После исследования домена Nodes стало понятно, что компоненты слоя Theme Components больше не являются независимыми. Они образуют связанный граф зависимостей.
    Необходимо изменить инфраструктуру построения компонентов.
    ++ 5.1. Изменить контракт ThemeComponentBuilderInterface
        Builder должен иметь доступ не только к своему ConfigurationDomain, но и к уже построенным компонентам темы.
        Например:
        ConfigurationDomain
        ThemeComponentCollection
        или аналогичный BuildContext.
    ++ 5.2. Изменить ThemeComponentCollectionBuilder
        Он должен строить компоненты последовательно, сохраняя каждый построенный компонент в коллекции.
        Каждый следующий Builder получает доступ к уже построенным компонентам.
        Схема построения станет такой:
            NodesComponentBuilder
                    │
                    ▼
            ThemeComponentCollection

                    │
                    ▼
            CompositionsComponentBuilder

                    │
                    ▼
            ThemeComponentCollection

                    │
                    ▼
    ++ 5.3. Обеспечить детерминированный порядок построения компонентов
        Поскольку появляются зависимости между компонентами, порядок их построения становится частью архитектуры.
        На текущем этапе достаточно обеспечить следующий порядок:

            Nodes
                ↓
            Compositions

        В дальнейшем список зависимостей можно будет расширять.

++ Этап 6. Интеграция Nodes с Compositions
    После изменения инфраструктуры выполнить первую интеграцию доменов.
    ++ 6.1. Изменить CompositionsComponentBuilder
        Builder должен получать уже построенный NodesComponent.
        Из него необходимо получить:
        NodeCollection
        и передать её в
        CompositionCollectionBuilder
    ++ 6.2. Построить полностью связанный граф объектов
   
        CompositionNode
                │
                ├── Composition
                └── Node
                
        Builder не должен оставлять неразрешённых ссылок.

Этап 7. Проверить инварианты модели
    После завершения построения должны выполняться следующие гарантии.
    Любая ссылка на Composition разрешена

        CompositionNode
            │
            ▼
        Composition

    или отсутствует.
    Любая ссылка на Node разрешена
        CompositionNode
            │
            ▼
        Node

    или отсутствует.
    Не существует "висячих" ссылок
    Такое состояние невозможно:
    CompositionNode(id="hero")
    если отсутствуют одновременно:
    Composition "hero"
    Node "hero"
    В этом случае Builder обязан завершиться специализированным исключением.

Этап 8. Подготовить фундамент следующих стадий Pipeline
    После этих изменений последующие стадии (Render Preparation, Materialization и другие) должны работать исключительно с объектной моделью Theme Components.
    Им больше не потребуется:
    обращаться к конфигурации;
    искать Node;
    разрешать ссылки;
    проверять существование ресурсов.
    Они будут получать уже полностью связанный граф:

    CompositionsComponent
            │
            ▼
    Composition
            │
            ▼
    CompositionNode
            ├── Composition
            └── Node
                    │
                    ▼
            ResolvedResource

Итоговая последовательность
✅ Расширить CompositionNode ссылкой на Node.
✅ Добавить поиск Node по id в NodeCollection.
✅ Расширить CompositionCollectionBuilder для разрешения ссылок на Composition и Node.
✅ Добавить специализированное исключение для неразрешённых ссылок.
⏳ Изменить инфраструктуру Theme Components, чтобы Builder имел доступ к уже построенным компонентам.
⏳ Изменить CompositionsComponentBuilder, чтобы он использовал NodesComponent.
⏳ Проверить, что после построения отсутствуют неразрешённые ссылки.
⏳ Передать последующим стадиям Pipeline полностью связанный граф объектов.

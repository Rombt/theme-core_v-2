Актуальный список проблем
1. Зафиксировать границу данных ThemeIR → Artifacts

Для Templates Artifacts получает:

Template
    ↓
TemplateTree
    ↓
TemplateNode
        ├── resource()
        ├── rendering()
        ├── slot()
        └── children()

Нужно проверить весь код Artifacts и устранить остатки прямой зависимости от ThemeComponents.

2. Реализовать получение содержимого Resource

Механизм теперь определён:

Resource::value()
    +
Target Architecture
    ↓
Representation Path
    ↓
File Content

Для Classic:

resources/components/{resource-id}/classic.php

Для Block:

resources/components/{resource-id}/block.html

Нужно привести TemplateResourceContentReader к этому контракту.

3. Определить обработку TemplateNode без Resource

Это остаётся отдельной задачей.

Например:

site-title
navigation
copyright
widgets

могут иметь:

resource = null

Нужно определить, как их содержимое готовится Artifacts на основании имеющихся данных ThemeIR и rendering.

4. Зафиксировать семантику rendering в Artifacts

Нужно определить, что конкретно делает Artifacts для каждого значения:

Inline
Template
Header
Footer
Sidebar
SearchForm
TemplatePart
Comments

Например:

Inline
→ содержимое становится частью текущего Artifact


Header
→ подготавливается отдельный Artifact
→ родительский Artifact получает механизм подключения header


TemplatePart
→ подготавливается отдельный Artifact
→ родительский Artifact получает механизм подключения template part

Это центральная задача Artifact Generation.

5. Определить рекурсивную обработку TemplateTree

Нужно зафиксировать алгоритм:

Template
    ↓
TemplateTree
    ↓
roots
    ↓
TemplateNode
    ↓
children

В частности:

когда читается содержимое Resource;
когда обрабатываются children;
как slot() влияет на объединение родительского содержимого и дочерних элементов;
что происходит при отсутствии Resource.
6. Разделить ответственность Generator и Renderer

Нужно окончательно зафиксировать:

ArtifactGenerator
    → принимает Template
    → определяет создаваемые Artifact
    → создаёт Artifact
Renderer
    → обрабатывает TemplateTree / TemplateNode
    → подготавливает содержимое

Generator не должен содержать логику обхода и рендеринга дерева.

7. Разделить Classic и Block стратегии

Нужно определить две реализации:

ClassicTemplateArtifactGenerator
ClassicTemplateTreeRenderer

и:

BlockTemplateArtifactGenerator
BlockTemplateTreeRenderer

Они используют одинаковую структуру ThemeIR, но:

читают разные файлы представления;
по-разному интерпретируют rendering;
могут создавать разные Artifact и связи между ними.
8. Определить полный результат работы одного Generator

Для одного:

Template

нужно определить:

какие Artifact создаются
↓
какие у них:
    id
    type
    destination
    content

Важно: один Template потенциально может приводить к нескольким Artifact, например при Header, Footer или TemplatePart.

9. Переработать текущий код Templates в Artifacts

После решений выше привести к новой модели:

ArtifactServiceDefinitionProvider
ArtifactGeneratorInterface


ClassicTemplateArtifactGenerator
BlockTemplateArtifactGenerator


ClassicTemplateTreeRenderer
BlockTemplateTreeRenderer
TemplateTreeRendererInterface


TemplateResourceContentReaderInterface
FileTemplateResourceContentReader
10. Удалить остатки старой архитектуры

После переработки проверить, чтобы не осталось логики вида:

Artifacts
    → ThemeComponents

или:

TemplateNode
    → готовый абсолютный путь

или старых специализированных способов получения содержимого Node.

Главная последовательность

Я бы решал в таком порядке:

1. Node без Resource
        ↓
2. Семантика rendering
        ↓
3. Рекурсивная обработка TemplateTree и slots
        ↓
4. Результат одного Generator: какие Artifact создаются
        ↓
5. Classic / Block стратегии
        ↓
6. Переписывание кода Artifacts
